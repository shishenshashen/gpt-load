# df-queue 稳定性加固（2026-10-18）

## 背景

`df-queue/queue-proxy.mjs` 是监听 3001 的排队网关：所有模型调用先在这里排队，再转给 gpt-load（127.0.0.1:3101）。它同时管着三件事：**出口并发闸门**（cap）、**排队与排队上限**、**上游故障时的换池重试**。

当天暴露了 8 个问题，其中 4 个造成过真实故障（最长一次 3001 在飞打满、上游并发为 0 持续 14–29 分钟，请求全部无响应）。本 PR 按「问题 → 根因 → 修复 → 验证」整理。

---

## P1 配置改了、重启就失效

**现象**：面板把出口并发设成 20，重启 3001 后回读仍是 10。
**根因**：启动序列只调 `applySettings()`，**从未调用 `loadSettings()`**，每次重启都回落到代码默认值（cap 10 / userQueueMax 20 / maxWait 180000）。盘上的 `settings.json` 形同虚设。
**修复**：`queue-proxy.mjs:1673` 启动时先 `await loadSettings()` 再 `applySettings()`，并打日志 `settings loaded: cap=… userQueueMax=… maxWaitMs=…`。
**验证**：启动日志 `settings loaded: cap=10 userQueueMax=200 maxWaitMs=300000` —— 200 / 300000 都不是代码默认值，只能来自读盘。

## P2 出口并发被钉死在常量

**根因**：`new http.Agent({ maxSockets: CAP })`，CAP 是模块常量 10。即使 `settings.cap` 改成 20，连接池上限仍是 10。
**修复**：`applySettings()` 里同步（`:88-89`）：
```js
agent.maxSockets = settings.cap;
agent.maxFreeSockets = settings.cap;
```
**保留 `keepAlive: true`**：改成 `keepAlive:false` 会让每条请求重建 TCP/TLS，握手开销压在出口延迟上，反而放大 524。

## P3 半死长连接焊死出口名额

**现象**：`health=200`，但 3001 在飞 10、gpt-load 并发 0 持续十几分钟，请求既无响应也无错误。
**根因**：`new http.Agent({ keepAlive: true, timeout: 0 })` —— 空闲连接永不过期，请求写进已被对端静默关闭的 socket 后一直等。
**修复**：`timeout: 30_000`（空闲 30 秒回收），保留复用。
**验证**：45 秒连续采样 `o` 与 `c` 完全同步（1→1、2→2）；20 并发同负载压测 p95 与改前持平（15728ms vs 15810ms），0 个 524。

## P4 排队逻辑缺陷：有空槽仍排队、排队上限失效

**现象**：出口只用了 6/10，请求却在排队，最长要等到 30 秒扫描才派发。
**根因**两条：
1. 请求完成后给该用户 150ms 冷却（`u.coolUntil`），而 `pump()` 只在「完成 / 入队 / 30 秒定时扫描」时触发——**冷却到期后没人再唤醒 pump**，空槽就一直晾着。
2. 每人排队上限取的是常量 `USER_QUEUE_MAX(20)`，页面上设的 `settings.userQueueMax(200)` 不生效，20 个之后就 429。

**修复**：
- `pump()` 在因冷却拿不到任务时，按最早的 `coolUntil` 补一次唤醒（`:360-372`）。
- 冷却只在「多用户」时生效；只有一个人排队时没有必要空等。
- `enqueue()` 改读 `settings.userQueueMax`（`:387`）。

**验证**：8559 个 5 秒采样中「`q>0` 且 `o<9`」= 1614 个，修复后同样的压测不再出现整段空槽；40 并发从「18 个 429」变成「40 个全 200」。

## P5 断流无处置：一条死流占名额 10 分钟

**现象**：上游开始返回后中途卡住，响应既不结束也不报错，出口名额被占死。
**根因**：断流阈值 `600_000ms`（10 分钟）。
**修复**：三档阶梯
- 30s 无新字节 → 记 `stream stall` 预警 + 给 SSE 客户端发保活注释
- 60s 无任何字节且**响应头尚未发出** → `noteFail` + 换下一个模型池重试（客户端无感）
- 90s 仍无数据 → `stream stall kill`，斩断上游与客户端连接，`done()` 释放名额

**关键配套改动**：为支持「60s 换池」，流式转发从 `ur.pipe(res)` 改为**首块数据到达才 `writeHead` + 手动转写**。原来收到上游响应头就立刻写头，HTTP 头只能发一次，发出后就没法再换模型了。
**验证**：非流式 20 并发 × 20 请求全 200（p50 10899ms / p95 14874ms）；流式 `stream:true` 返回 200、19 个 `data:` 行、含 `[DONE]`。

## P6 假 200：上游回 200 但 0 字节

**根因**：上游返回 `200 OK` 后一个字节都没吐就 `end`，原逻辑会原样透传，客户端收到「成功但空」的响应。
**修复**（`:736-762`）：`end` 时若一个字节都没收到 → `noteFail` + 换池；池耗尽则回 `502 empty_response`，不再给假成功。

## P7 监控口径误导：把「流式传输中」当成「卡单」

**现象**：看板长期显示「卡单 6~7」，据此误判网关故障、并把 cap 从 10 降到 4。
**根因**：`o − c` 被定义为卡单。但 gpt-load 的 `concurrency.current` 只统计「等首字节 / 上游处理中」，**首字节返回后进入流式传输就不再计入**；而 3001 的 `inFlight` 要算到响应结束。两者之差主要是正在传输的流式响应（实测首字节 p50 3.6–4.0s、总耗时 p95 20s+）。
**修复**：
- 后端新增真卡单指标：`ACTIVE` 记录 `lastByteAt`，`adminStats` 输出 `stalled`（≥60s 无新字节的请求数）与 `maxIdleMs`。
- 前端把「卡单 o−c」改为「传输中（流式，正常）」，真卡单改用 `stalled`；另外显示「近 60s 首字节超时次数」（`ttfbTimeouts` 60 秒滑动增量）。
**验证**：接口回读 `cap=10 o=7 q=0 c=8 stalled=0 maxIdleMs=9472` —— 与真实情况一致（无卡单）。

## P8 探针假绿

**根因**：`probeModel()` 用 `.env` 的 `AUTH_KEY` 调 `/v1/chat/completions` 只拿到 401（1ms），而代码把 `status < 500` 一律当「通道活着」，日志持续 `probe OK`。
**修复**：401 记为「探针凭据无效」，不算健康、也不禁用模型；判定网关健康必须发真实补全短请求。

## 实时监控（本轮同样重要的另一半）

上面 P7 只讲了「卡单指标算错」。监控这块的整合改动比那一条大，单列出来。

### M1 指标语义：流式传输中 ≠ 卡单

**问题**：看板长期显示「卡单 6~7」，据此误判成网关故障，甚至把出口并发从 10 降到 4（错误动作，已回滚）。
**根因**：`o − c` 被当成卡单。`o`（3001 在飞）算到响应结束，`c`（gpt-load 并发）只算到首字节返回。差值 = **正在传输流式响应的请求**，是正常状态。
**修复**：该指标改名「传输中（流式，正常）」，不再触发告警。

### M2 新增真卡单指标：`stalled` / `maxIdleMs`

**问题**：换成「传输中」后，真正卡住的请求没有指标可看。
**修复**：
- 后端 `ACTIVE` 每条记录 `lastByteAt`（上游每次吐数据都刷新）；`adminStats()` 输出
  - `stalled` = 已派发且 **≥60s 无新字节**的请求数
  - `maxIdleMs` = 当前最久的一条空闲多久
- 前端能量槽底部显示「卡单 N（最久 Xs 无数据）」，只有 `stalled > 0` 才变琥珀。

**验证**：接口回读 `stalled=0 / maxIdleMs=9472`，与「当前无卡单、最久一条只空闲 9.5 秒」一致。

### M3 近 60 秒首字节超时次数

**问题**：`ttfbTimeouts` 是进程启动以来的累计值，看总量无法判断「现在是不是在恶化」。
**修复**：前端维护 60 秒滑动窗口，对 `ttfbTimeouts` 做差分，显示「近 60s 首字节超时 N」；配合 `stalled` 一起作为告警依据。

### M4 等待时间无样本时显示 `—`，不显示 0

**问题**：看板「平均等待 / P95 等待」在重启后一直显示 0，被误读成「等待时间为 0」。
**根因**：等待样本是内存数组（最多 1000 条），重启清零；而且只在 `wait > 5ms` 时才记录——没排队就没有样本。
**修复**：无样本时显示 `—` 并注明「本次启动后无排队」，不再用 0 冒充。

### M5 设置项语义同步

「卡单告警阈值」→「首字节超时告警阈值」，说明改为「近 60 秒首字节超时次数 ≥ 该值才告警（o−c 是流式传输中，不算卡单）」。

## 未包含（需要单独决策）

1. **settings.json 类型校验**：当前「合法 JSON 但字段类型错」（如 `cap:"ten"`）会被静默接受，随后 `inFlight < "ten"` 恒 false ⇒ 全站请求永不派发。实测确认属「静默吃坏值」，建议加字段校验 + 坏文件另存。
2. **stats 面板常量显示**：`/df/queue/stats` 的 `userQueueMax / maxWaitMs / queueMax` 仍取代码常量，页面从这里取值再保存会把旧值写回配置。
